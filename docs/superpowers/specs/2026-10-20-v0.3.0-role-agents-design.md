# my-tech-team v0.3.0: one agent per role

Date: 20 Oct 2026. Status: **approved by the PM (20 Oct 2026)**. Research: [`docs/research/agent-models.md`](../../research/agent-models.md). Slides: [`docs/slides/v0.3.0.html`](../../slides/v0.3.0.html).

## Goal

Each role runs on a model, effort level and tool set that fit its job. The lead stops running every role on the PM's session model with every tool.

## Decisions (PM, 20 Oct 2026)

| Decision | Choice |
|---|---|
| Design | One Claude Code agent per role, as in the table below |
| Marketer model | Sonnet |
| Scout helper | Yes: Haiku, read-only, for lookups. Not a role; the PM never briefs it |
| Reviewer model | Opus, high effort |

## 1. Agents

The plugin ships `agents/<name>.md`. Claude Code names them `my-tech-team:<name>`. Each agent preloads its role's skill, so the rules stay in the skill and don't repeat in the agent file.

| Agent | `model` | `effort` | Tools | Notes |
|---|---|---|---|---|
| (lead) | — | — | — | Stays in the PM's session. No agent file |
| `developer` | `sonnet` | `medium` | all | |
| `tester` | `sonnet` | `medium` | all | |
| `reviewer` | `opus` | `high` | `Read, Grep, Glob, Bash, Skill, ReportFindings` | No Edit or Write. Feature-level review: the lead passes `xhigh` or says so in the brief |
| `qa` | `sonnet` | `medium` | all (inherits browser and simulator tools) | |
| `marketer` | `sonnet` | `medium` | `Read, Write, Edit, Glob, Grep, WebFetch, WebSearch, Skill` | No Bash |
| `scout` | `haiku` | `low` | `Read, Grep, Glob, Bash` | Answers "where is X / what calls Y" with file:line. No skill |

- Plugin agents can't set `hooks`, `mcpServers` or `permissionMode`; they keep the PM's permission mode. That is what we want.
- `tools` omitted = all tools the session allows, including MCP tools (QA needs the browser and simulator).
- The skills stay unchanged and portable. Other AI tools ignore `agents/`.

## 2. Lead dispatch rules (lead skill, Claude Code part)

- Dispatch each role to its agent, `my-tech-team:<role>`. Always name the agent; never rely on a generic agent that inherits the session model.
- Use `my-tech-team:scout` for lookups instead of reading many files in the lead's context.
- **Escalation ladder:** start at the agent's defaults. After a failed review or test round on the same item, re-dispatch with higher effort. After a second failure, one tier up (`model: opus`). Still stuck: blocker to the PM.
- **Start the developer on Opus** when the item changes the data model or a public API, touches auth, payments or personal data, or spans several modules. Say why in the brief.
- **Team setup override:** a project can set a role's model or effort under Team setup ("Agent models"). The lead passes it on each dispatch.
- Briefs are self-contained: the task, interfaces, decisions so far and files to read. Never "read the whole plan".
- Run in parallel only independent items or read-only checks.
- **Marketer briefs name every input file** (voice file, QA evidence, changelog, earlier drafts): the marketer has no shell, and in Claude Code 2.1.236 no search tools, so it can only open paths it is given.

## 3. Spike results (21 Oct 2026)

All three unknowns pass: `effort` works, `skills: [my-tech-team:<role>]` preloads the skill, and the guard hook runs for agent Bash calls. Details: [`docs/testing/results/v0.3.0-spike.md`](../../testing/results/v0.3.0-spike.md). Changes from the spike: Grep and Glob are absent in Claude Code 2.1.236, so limited agents keep Bash for search (the scout is not strictly read-only; the guard and the PM's permission mode still apply); limited agents list `Skill`. The reviewer gets no `Agent` tool, so it can't hand work to an agent that has edit tools; the `security-review` and `code-review` skills may run without their own subagents inside the reviewer agent (checked in the v0.3.0 runs).

### Original unknowns

1. `effort` frontmatter takes effect in a plugin agent.
2. `skills:` preloads a plugin skill into a plugin agent, and the exact name string.
3. The plugin's PreToolUse guard hook fires for a plugin agent's Bash call.

Also confirm `model` frontmatter is used (the subagent's messages show the Sonnet or Opus model ID) and that the reviewer can't use Edit or Write.

If 1 fails: drop `effort` from the files and put the effort in the lead's dispatch instead. If 2 fails: the agent body tells the agent to load its skill first. If 3 fails: stop and bring it to the PM; host safety must not get weaker.

## 4. Testing

- CI lint: every agent file has `name`, `description`, `model`; `reviewer` and `scout` have no Edit or Write; `marketer` has no Bash; each role agent preloads its skill.
- Rerun each role's pressure scenarios with the role's agent and model (developer D1–D5, tester T1–T2, QA Q1–Q4, marketer M1/M1b, reviewer R1–R3). A role that fails a scenario that passed on Opus: raise its effort and rerun; if it still fails, it goes to `opus` and the result says so.
- Lead scenario: the lead dispatches named agents, uses scout for a lookup, and follows the escalation ladder.
- Real check: in a `--plugin-dir` session, `/agents` lists six `my-tech-team:` agents with their models.

## Out of scope

- Per-route cost measurement with an eval harness (we compare pass/fail and turns in the pressure tests only).
- `opusplan` or advisor pairings.
- Agents for other AI tools.
