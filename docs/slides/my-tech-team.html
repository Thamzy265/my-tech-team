The team

Six roles, plus you

You: project manager

Decide, approve merges and releases, and publish. You are not a skill.

Lead

Plans, designs large items, writes the UI spec and the privacy screen, runs the gates, reports to you, merges.

Developer

Builds to the brief, test-first. Can push back on an unclear spec.

Tester

Tries to break it. Adds regression, UI-state and abuse-case tests.

Reviewer

Reviews code, design, security and privacy. Never the author.

QA

Checks the real product: acceptance, accessibility, privacy, marketing claims.

Marketer

Research, launch comms and content. Never publishes.

How one item flows

Every item passes every gate

Lead sizes it, then designs it if large→ You approve the slides (large items)→ Developer builds→ Tester breaks it→ Reviewer approves (loop)→ QA checks it for real→ You approve the merge

Small item

One module. No new data store, integration, trust boundary or personal data. No design note or slides.

Large item

Everything else. It gets a design note, a UI spec if there is UI, a privacy screen and a slide deck for you.

If a gate does not apply, the log says "n/a — reason". It is never skipped silently.

MVP first

Build the essentials now. Note the rest with a trigger.

Can wait until after the MVP

  • Caching, replication, sharding, queues for scale
  • Microservices (stay a modular monolith)
  • Formal SLOs and dashboards
  • Tuning beyond the basic budget
  • Nice-to-have features

Never deferred

  • Security basics and authorisation checks
  • Privacy: minimal data, delete, export, consent
  • Data integrity, reversible migrations, backups
  • Timeouts and safe retries
  • Tests, review, QA, basic accessibility

Later list in docs/PLAN.md, for example: "Caching for /search, trigger: p95 > 500 ms or > 1,000 daily users." You change the phase (MVP → Growth → Scale), and the lead then reviews the list with you.

System design

How systems and data are built and run

The lead's 12 steps (large items)

  • Requirements, scope, non-goals
  • Top 3 qualities, and a load estimate
  • Domain and data model, consistency, migrations
  • Two options and their trade-offs
  • Failure planning, observability, rollout and rollback
  • Trust boundaries, then an ADR if hard to reverse

Guard rails

  • Modular monolith first
  • Design for about 10× load, not 1000×
  • Timeouts and bounded retries everywhere
  • Database changes: expand → migrate → contract
  • The developer gets a short data/API checklist; the reviewer checks for drift

Sources: DDIA 2nd ed. (2026), Fundamentals of Software Architecture 2nd ed., Google SRE, Release It!, A Philosophy of Software Design, Building Evolutionary Architectures.

UI / UX

Spec before code, checked after

Lead writes the UI spec

  • User, task, flow
  • Every state: loading, empty, error, long text, offline
  • Breakpoints down to 320 px
  • Accessibility notes (WCAG 2.2 AA)

Developer builds to it

  • Semantic structure first
  • Design tokens, no hard-coded values
  • No unsafe HTML, no secrets in the app

Tester, reviewer, QA check it

  • Every state and keyboard-only use
  • Automated accessibility scan
  • Real app: zoom, contrast, screen reader

Sources: Nielsen Norman Group heuristics, Krug, Refactoring UI, Atomic Design, WCAG 2.2, W3C design tokens.

Security

Reviewed twice: per branch and per feature

Every branch

  • Checklist from the OWASP Top 10:2025 and CWE Top 25
  • Authorisation, injection, SSRF, secrets, dependencies
  • LLM risks if the product uses AI

Every finished feature

  • The combined result on main
  • Catches gaps between the API and the UI
  • The feature is not "done" until this passes

Blocks the merge

A Critical or High finding · a leaked secret · missing authorisation on a new endpoint · a reachable Critical or KEV-listed dependency. Only you can accept a known risk.

Data privacy · UK + EU

Each role checks its part

RoleChecks
LeadData fields, purpose, lawful basis, retention, DPIA screening, children, vendors
ReviewerNo personal data in logs or URLs; encryption; deletion jobs; SDKs only after consent
QANothing tracks before consent; Reject is as easy as Accept; export and delete work
MarketerRecorded consent, opt-out in every message, privacy claims backed by evidence

Always comes to you: breaches (72-hour clock), DPIAs, sensitive or children's data, lawful basis, new processors or transfers, regulators. UK GDPR as amended by DUAA 2025, PECR, EU GDPR, ePrivacy. Not legal advice.
