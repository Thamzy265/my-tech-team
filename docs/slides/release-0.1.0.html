What is in it

Six skills, one plugin, two install routes

lead

Plans, sizes, designs large items (system design, UI spec, privacy screen, deck), runs the gates, reports to you, merges after you approve.

developer

Builds to the brief, test-first. MVP-only, with Later lines that have triggers. Never defers the essentials.

tester

Adds tests that fail on the old code: edge, failure and abuse cases. Never touches production code.

reviewer

Code, design, security (OWASP 2025) and privacy review, per branch and per feature. Blocks on real risk.

qa

Checks the real product: acceptance, accessibility, UK + EU privacy, marketing claims. Writes your check steps.

marketer

Research, launch copy and content from QA evidence only. Never publishes.

Claude Code: /plugin marketplace add Thamzy265/my-tech-team, then /plugin install my-tech-team@my-tech-team. Other tools: copy skills/* into .agents/skills/. About 500 tokens per session.

Release and rollback

How it ships, and how to undo it

1 You approve PR #1→ 2 Merge to main→ 3 Set the date in CHANGELOG, tag v0.1.0→ 4 GitHub release→ 5 Install from GitHub and check 6 skills

Rollback

Delete the tag and the GitHub release, and revert the merge commit. Users who installed it run /plugin uninstall my-tech-team@my-tech-team.

Risk

Low. It is public text, with no code that runs on install. The worst case is wrong advice in a skill, which the next version fixes.

Decisions needed

Three yes/no answers

1. Approve and merge PR #1 into main?

Recommendation: yes. All checks are green and the reviews are addressed.

2. Tag and publish the v0.1.0 GitHub release?

Recommendation: yes, straight after the merge.

3. Then switch project-deck to the plugin?

Recommendation: yes, as a separate PR in project-deck. Your FlutterDeck rules move into its CLAUDE.md. I will plan it and show you before changing that repo.
